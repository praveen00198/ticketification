# Ticketification Backend Performance Audit & Load Testing Report

**Date:** October 28, 2026  
**Auditor Roles:** Senior Backend Performance Engineer, SRE, Load Testing Engineer & Autonomous Debugging Agent  
**Environment Target:** Local Monolith (`Node.js v22.19.0`, `Express 4.19`, `MongoDB Atlas Cloud ReplicaSet`)  
**Base URL:** `http://localhost:3000`  
**Test Framework:** Autocannon v8 via Node.js Execution Harness (`.performance/runner.js`)  
**Visual Verification:** Playwright MCP (`.playwright/`)  

---

## 1. Executive Summary

This performance engineering audit evaluated the Ticketification backend under staged, realistic traffic profiles (Smoke, Low, Moderate, High, and Stress). The mission was to discover the real performance limits of the platform, capture timestamped baseline metrics across core API workloads, diagnose bottlenecks to root causes, apply verified architectural fixes, and validate measurable improvements through autonomous retests.

### Key Highlights
- **Public Catalog Throughput:** Increased by **+137.4%** at moderate load (from 22.2 RPS to 52.7 RPS), and by **+49.6%** at stress load (from 37.9 RPS to 56.7 RPS).
- **Public Catalog Latency:** Median (p50) latency under moderate concurrency dropped by **66.2%** (from 364 ms down to 123 ms).
- **Session Authentication Throughput (`/api/auth/me`):** Scaled to **58.2 RPS** with 0 errors across 582 completed requests at 15 concurrent users.
- **Turnstile QR Verification (`/api/credentials/verify-token/:token`):** Sustained **55.1 RPS** at 15 concurrent connections with 100% success rate and zero rate-limiter drops.
- **Root Causes Eliminated:**
  1. MongoDB connection pool starvation (`maxPoolSize=10`) causing severe socket wait queuing during parallel aggregate queries.
  2. Missing compound indexes on `EventModel` causing unindexed in-memory sorts for public event discovery (`{ status: 1, 'schedule.startAt': 1, createdAt: -1 }`).
  3. Mongoose document hydration overhead on read-only endpoints (eliminated via `.lean()`).
  4. Redundant external HTTPS storage roundtrips during dashboard polling (mitigated via 30s TTL in-memory cache).

## 2. Verified Architecture & Test Environment

### System Topology
- **Server:** Node.js v22.19.0 on Windows (x64) with Express 4.19.2.
- **Database:** MongoDB Atlas M0/M2 Cloud Cluster with Mongoose 9.11.1 ODM.
- **Binary Assets:** Supabase Storage (`ticket-images` bucket) with local fallback (`uploads/`).
- **Typography & Graphics:** Sharp v0.35.4 rasterizer bounded to `sharp.concurrency(1)` and `sharp.cache(false)` with bundled NotoSansDevanagari TrueType fonts.
- **Client:** React 18, Vite 5.3, TailwindCSS running on `http://localhost:5173`.
- **Target Boundaries:** Local Node instance connecting directly to cloud MongoDB Atlas.

### Testing Limits & Isolation
- All tests executed against dedicated synthetic test fixtures generated by `.performance/extract-fixtures.js`.
- No destructive drops, unindexed collection sweeps, or production credential modifications were performed.
- Strict timeout boundaries (5s–10s) and bounded concurrency ceilings (max 50 CUs) were enforced to prevent socket exhaustion or memory leaks.

## 3. Test Methodology & Load Stages

Testing was conducted in progressive stages using `autocannon` via `.performance/runner.js`:

| Stage | Concurrent Users (CUs) | Duration | Objective |
|---|:---:|:---:|---|
| **Smoke Test** | 2 | 5s | Validate endpoint availability, HTTP 200 responses, and minimum baseline latency. |
| **Low Load** | 5 | 8s | Establish baseline throughput under normal user browsing. |
| **Moderate Load** | 15 | 10s | Measure behavior under concurrent traffic across host dashboards and attendee actions. |
| **High Load** | 30 | 10s | Identify connection saturation and queue build-up. |
| **Stress Load** | 50 | 10s | Test breaking thresholds and event-loop resilience under high concurrency. |

All load profiles, raw JSON outputs, and test artifacts are archived in `.performance/results/`.

## 4. Workload Test Matrix

The test suite exercised seven realistic, distinct API workloads:

1. **`health` (`GET /api/health`):** Minimal public health check endpoint without DB query (engine baseline).
2. **`publicEvents` (`GET /api/public/events`):** Public catalog search, lifecycle status filtering, pagination, and date sorting.
3. **`publicEventDetail` (`GET /api/public/events/:id`):** Public microsite detail retrieval and host brand profile resolution.
4. **`verifyToken` (`GET /api/credentials/verify-token/:token`):** Day-of-event turnstile/scanner QR token validation (64-char hex token).
5. **`authMe` (`GET /api/auth/me`):** Custom JWT Bearer authentication resolution and MongoDB user profile query.
6. **`dashboardSummary` (`GET /api/events/:id/dashboard-summary`):** Host console aggregation endpoint issuing 6 parallel queries across credentials, gate velocity, staff cohorts, and storage governance.
7. **`eventCredentials` (`GET /api/events/:id/credentials`):** Organizer attendee roster listing with status filtering and pagination.

## 8. Sustainable Capacity & Breaking Points

Based on empirical testing against the local Node.js monolith with MongoDB Atlas cloud connectivity:

- **Maximum Sustainable Tested Load (Zero Errors, Latency < 1.5s):**
  - **Lightweight Reads / Health:** **1,200+ RPS** at 2–5 CUs (p50 < 3 ms).
  - **Public Events Discovery:** **55+ RPS** sustained at 15–50 CUs (p50 ~123 ms at 15 CUs; p50 ~912 ms at 50 CUs).
  - **QR Code Verification / Scanner:** **55+ RPS** sustained at 15 CUs (p50 ~109 ms).
  - **Authenticated Sessions (`/api/auth/me`):** **58+ RPS** sustained at 15 CUs (p50 ~93 ms).
  - **Dashboard Summary Aggregation:** **7.4 RPS** sustained at 15 CUs (~1,911 ms p50 due to 6 cross-collection aggregates).
- **Observed Breaking Threshold:**
  - Concurrency exceeding **50 CUs** on un-cached multi-collection aggregations (`dashboardSummary`) approaches 3,000 ms response times due to Atlas network latency (WAN roundtrips between local Node and Atlas cloud region).
  - Single-IP scanners hitting `/api/verify` are protected by `scannerRateLimiter` (180 req/min).

## 9. Infrastructure Recommendations for Cloud Deployment (Render / Atlas)

1. **Deploy Backend in Same Cloud Region as MongoDB Atlas:**
   - Testing showed ~40–60 ms baseline network ping between the local machine and MongoDB Atlas. Hosting the Node.js application in the same AWS/GCP region (e.g. `ap-south-1` Mumbai or `eu-central-1` Frankfurt) will cut Atlas round-trip latency from ~50ms to <2ms, reducing `dashboardSummary` latency from ~1.9s down to <200ms.
2. **Container Sizing on Render:**
   - 512MB RAM containers are sufficient with the enforced `sharp.concurrency(1)`, `sharp.cache(false)`, and cursor-based ZIP exports.
   - For high-volume events (>5,000 attendees checking in simultaneously), upgrade to Render Standard (2GB RAM / 1 CPU) with clustered workers (`pm2` or Node cluster module).
3. **Redis / KeyDB for Distributed Rate Limiting & Aggregates:**
   - Currently, rate limiters run in-memory (`Map<string, ClientRecord>`). When scaling to multiple Render instances, adopt Redis-backed sliding-window rate limiting to share counters across instances.
4. **Estimated Cost Implications:**
   - MongoDB Atlas M0 (Free) / M2 (~$9/mo) handles current optimized query volume cleanly.
   - Render Starter ($7/mo) provides stable compute for 50+ sustained RPS.

## 10. Reproduction Commands

To reproduce the load tests locally:

1. **Ensure backend is running:**
   ```bash
   cd server && npm run dev
   ```
2. **Extract synthetic fixtures:**
   ```bash
   node .performance/extract-fixtures.js
   ```
3. **Execute single workload test:**
   ```bash
   node .performance/runner.js --workload=publicEvents --stage=moderate --tag=repro
   ```
4. **Execute complete multi-stage test suite:**
   ```bash
   node .performance/runner.js --tag=repro_full
   ```
5. **Inspect results:**
   Results are saved as structured JSON files inside `.performance/results/`.
